Unified Service Scheduler

A backend service that replaces manual dealership booking: a customer requests a service appointment for a vehicle, service type, dealership and time; the system verifies that both a service bay and a qualified technician are free for the entire service duration, then persists a confirmed appointment linking customer, vehicle, technician and bay.

§2

Architecture

  • API Gateway / LB (deployment concern) — TLS, authentication, rate limiting, fan-out across stateless replicas.
  • REST Controllers — HTTP boundary: bean-validate requests, map domain exceptions to a uniform JSON error, hold zero business logic.
  • AvailabilityService — read-only, non-binding probes (day slots, available technicians) used by the UI; reserves nothing.
  • BookingService — the transactional core (requirements 2 + 3): locks the vehicle and dealership, re-checks availability, writes the appointment atomically.
  • Repositories — Spring Data JPA; the availability queries express interval overlap as a NOT EXISTS subquery.
  • Database — source of truth; schema & seed owned by Flyway (ddl-auto=validate), versioned like code. Oracle in production, H2 for dev/test.
  • Observability stack — Actuator health, Micrometer/Prometheus metrics, tracing with trace/span ids in logs.

Domain model

A ServiceType carries a durationMinutes and a requiredSkill; a Technician holds a set of skills. A booking is feasible only when a technician’s skills contain the service’s requiredSkill.

§3

Data flow — the booking path

Interval overlap rule. Two windows overlap iff existing.start < requested.end AND existing.end > requested.start (half-open intervals, so back-to-back slots don’t collide). This exact predicate lives in every availability query.

Correctness under concurrency

The naïve “check availability, then insert” is a check-then-act race: two requests can both see the last bay as free and double-book it. Instead, book() runs in one transaction that takes two pessimistic write locks in a fixed order — vehicle first, then dealership — so bookings serialize per dealership and each request sees the committed effect of the previous one before it checks and inserts.

Proven by SchedulerIntegrationTest: 8 threads (distinct vehicles) hit the same capacity-2 slot → exactly 2 confirmed, 6 rejected, never 3. The vehicle lock also makes the same-vehicle guard race-safe across different dealerships.

Same-vehicle guard. A vehicle can only be serviced in one place at a time. Before reserving, the booking checks — with the same overlap predicate — whether the vehicle already has a CONFIRMED appointment in the window and rejects with 409 (DuplicateBookingException). The per-transaction vehicle lock makes it safe under load.

Alternatives considered

  • Chosen — per-dealership pessimistic lock: simplest thing that is provably correct; real-world contention per dealership is low.
  • Finer-grained: lock only the specific technician + bay rows with SELECT ... FOR UPDATE (well supported by Oracle) instead of the coarser per-dealership lock. Higher peak concurrency, more complexity.
  • Optimistic: @Version + retry — ideal when contention is rare.

Appointment lifecycle & slot release

A slot is not freed by the clock — it is freed by a status transition. A booking is created CONFIRMED, the only status the availability queries count. When the work is done the service desk records the technician sign-off (→ COMPLETED); a booking can also be CANCELLED. Either transition moves it out of CONFIRMED, so that technician + bay are immediately available again for the window.

The admin console (/admin) is where staff drive this — sign-off is the operational answer to “is this slot still occupied?”. No login: staff pick their dealership and manage only that location’s requests. When booking, the customer may pick a qualified, free technician (GET …/available-technicians); if not, the first qualified free one is auto-assigned — so a booking is always fulfillable and never overbooks.

A Quick-Book front-end (/) demonstrates the user experience — a service-first flow (service → nearest/usual dealership → open slot → confirm) wired to the live API. §6

Observability strategy

  • Logging — structured, with trace/span correlation ids in the log pattern (%X{traceId}/%X{spanId}). Each booking logs appointment id, dealership, service type, technician, bay and window at INFO.
  • Metrics — /actuator/prometheus exposes JVM, HTTP server latency histograms per endpoint, Hikari pool and JPA metrics. Add business counters bookings.confirmed / bookings.rejected{reason}.
  • Tracing — Micrometer Tracing spans per request, propagated to the DB call; export to Zipkin/Tempo via OTLP in prod.
  • Health — /actuator/health with a DB readiness check (liveness/readiness split for Kubernetes probes).
  • Golden signals map cleanly: latency (HTTP timer), traffic (request count), errors (4xx/5xx counters), saturation (pool + JVM gauges).
§7

Building for the future

  • Scalability — stateless service; scale by replicas. Booking contention is isolated per dealership, so write concurrency grows with the fleet. DB is the shared bottleneck → pooling, read replicas for probes, partition by dealership/region.
  • Performance — availability is an indexed NOT EXISTS query, backed by composite indexes on (technician_id, start_time, end_time) and (service_bay_id, start_time, end_time). Probes are cacheable at the edge.
  • Reliability — ACID transactions, Flyway-controlled schema, uniform error contract, future idempotency keys to make retries safe.
  • Maintainability — clean layering (web → service → repository → domain), DTOs decoupled from entities, single exception→status mapping, layered test pyramid.
  • Security & supply chain — authN/Z at the gateway, bookings scoped to the caller’s customer id; dependencies scanned (Trivy) in CI with transitives pinned to CVE-patched versions; DB secrets from environment, never source.

Roadmap (not implemented): appointment reschedule · real staff/customer auth · idempotency keys · technician shift calendars & breaks · “next available” multi-slot search · outbox + AppointmentConfirmed events · a database-level overlap guard as defense-in-depth.

§8

Deployment topology & disaster recovery

The service is stateless, so it runs as several replicas (pods) inside a Kubernetes cluster fronted by an internal load balancer (a Kubernetes Service / Ingress) that only routes traffic within that cluster. For resilience we run two clusters in two regions, and a network-level global load balancer (DNS/anycast, L4, health-checked) routes external traffic across them.

Two-tier load balancing. The global LB is the only externally-reachable entry point and decides which region serves a request; the internal LB inside each cluster decides which pod. They are separate concerns — the internal LB is never exposed outside Kubernetes.

Database & failover (active–passive with Oracle Data Guard). Region A holds the primary; Oracle Data Guard ships redo to a physical standby in Region B, continuously in sync. Running Data Guard in Maximum Availability (SYNC redo transport) gives a near-zero RPO without sacrificing primary availability if the standby is briefly unreachable. Normally all writes go to A. If A’s health checks fail, Fast-Start Failover (an observer promotes the standby automatically) activates Region B and the global LB drains traffic to it — a low RTO with no manual step. Optionally each region runs Oracle RAC for intra-region node redundancy, with Data Guard covering the cross-region disaster case. Because bookings need a single writer, this active–passive shape (one open primary at a time) preserves the §3 correctness guarantees; an active–active variant would need conflict-free write routing (e.g. sharding by dealership/region). Flyway runs identical migrations per deployment, so both regions share one schema version.

§9

How GenAI assisted the design

GenAI (Claude) was used as a design & implementation accelerator — every output reviewed and validated against a passing build and the test-proven concurrency guarantee.

  • Requirement decomposition — turned scenario prose into the §1 mapping and the domain model, surfacing the implicit “qualified technician = skill match” constraint early.
  • Concurrency reasoning — enumerated check-then-act failure modes and the fix spectrum (pessimistic / optimistic / database overlap constraints); the per-dealership lock was chosen deliberately.
  • Overlap correctness — sanity-checked the half-open predicate so back-to-back slots don’t false-conflict.
  • Boilerplate acceleration — entities, DTOs, repositories, exception→HTTP mapping, Flyway DDL/seed, and test scaffolding, then refined by hand.
  • Test design — proposed the latch-gated concurrency test asserting “successes == capacity”, which became the key correctness proof.
  • Bug caught in review — a live smoke test exposed a timezone shift (hibernate.jdbc.time_zone=UTC skewing zone-less LocalTime); root cause was a shadowed test config.

Guardrails: AI suggestions were treated as drafts — every claim is backed by a passing test or a live run, generated queries were read for correctness and indexing, and trade-offs were decided rather than accepted by default.
